# Performance evidence and repeatable benchmarks

Local software measurements: Intel x86_64, macOS 15.8.1, Python 3.12.3. Device data is
generated by the simulator, **not acquired from an IDS camera or USB bus**. Nominal 18.2 fps
is a configured simulated pacing target. Three-second runs are short throughput checks,
not sustained-storage, thermals, 30-minute, or reference-camera acceptance tests.

| Sequential local run | Recorded | Writer throughput | Result |
| --- | --- | --- | --- |
| 4056x3040 BayerRG12p, 18.2 nominal fps, 3 s | 53 frames / 980,254,080 bytes | 327.4 MB/s | all indexed CRCs verified |
| Same geometry/rate with 8 concurrent snapshot requests | 54 frames / 998,749,440 bytes | 329.5 MB/s | CRCs and exact snapshot bytes verified |

Snapshot request latency was 24.9–54.2 ms in the saved run. Main recording continued with
zero reported simulated losses/application drops/incompletes; recorder queue peaks were
3 and 2 frames respectively. Frames received before recording attachment or after detach
are counted separately as deliberately discarded, and retention evictions are not recording
drops. Short-window fps includes startup/last-frame quantization; inspect the JSON windows,
durations and recording interval rather than interpreting an average as a guaranteed rate.
MB/s is decimal; queue/pool/segment CLI limits labelled MiB use binary bytes.

When both full-resolution workloads were run together, the snapshot workload exceeded its
128 MiB bounded queue and raised `RecordingOverflowError`. This is an observed storage
contention limitation; the sequential results do not promise lossless operation under competing
I/O. Do not fix sustained pressure by concealing drops. Measure actual SSD/controller behavior.

Reports: `benchmarks/simulated-4056x3040-12p.json` plus `.txt`, and
`benchmarks/simulated-concurrent-snapshots.json`. They include configuration, counts/losses,
queue peaks, integrity, bytes and throughput; the CLI report also includes CPU time, peak RSS,
receive-rate windows and checksum readback duration. Export timing is unknown (`null`) when
no export was performed. Stress reports include each snapshot latency. Temporary raw data
is removed after checksum and reference verification on successful runs, avoiding huge
repository artifacts. Failed temporary benchmarks are also cleaned up; use CLI `--output`
to retain partial recordings for investigation. CPU time covers capture plus readback;
capture duration and checksum readback duration are reported separately.

```sh
scicam benchmark --camera simulated --width 4056 --height 3040 --pixel-format BayerRG12p \
  --fps 18.2 --seconds 3 --report measured
python benchmarks/capture_stress.py --width 4056 --height 3040 --pixel-format BayerRG12p \
  --fps 18.2 --seconds 3 --snapshots 8 --report snapshots.json
```

Run the commands sequentially for isolated measurements. Use longer runs and `--output`
to retain a CLI recording. `scicam camera-test --camera <id>` measures reception without
recording. On hardware, first inspect supported formats and actual readback, then compare
`--usb-mode sync` and `--usb-mode async` with equal pool/settings/storage. Native transfer
modes and both Mac architectures remain NOT TESTED here. Keep all counters whose meanings
are unverified unknown; frame-ID gaps alone do not prove the number of missing exposures.

Memory consists of the native pool, bounded recorder queue (including in-flight frames),
retention ring, at most configured concurrent pinned snapshot payloads, one received frame,
and optional downstream conversions. Shared frame references avoid duplicating payloads,
but caller-held frames and decoded arrays require their own budget. Do not allocate 64
full-resolution buffers blindly. Defaults are 4 native buffers with 128 MiB cap, a 16-frame/
128 MiB recorder queue and a 16-frame/64 MiB retention ring. Snapshot admission defaults to 8.

No C/Rust acceleration was added: the software path is profiled first, and native bridge
work requires measured GI copying/throughput limitations on an actual supported machine.
